# \# Unity Gameplay Architecture

# 

# 이 구조의 목적은 책임을 분배하기 위해 처음부터 많은 객체를 만드는 것이 아닙니다.

# 

# 먼저 작은 구조로 플레이를 구현하고, 기능이 복잡해졌을 때 기존 책임을 적절한 객체로 쉽게 이동할 수 있도록 구성하는 것을 목표로 합니다.

# 

# 완성된 구조를 미리 만드는 대신, 실제 개발 과정에서 드러나는 경계를 따라 확장합니다.

# 

# \---

# 

# \## 코드 읽는 순서

# 

# 플레이의 전체 실행 흐름은 다음 순서로 확인합니다.

# 

# ```text

# SceneRoot

# &#x20;   ↓

# Director

# &#x20;   ↓

# Flow

# &#x20;   ↓

# Actor / Viewer

# &#x20;   ↓

# Module

# ```

# 

# System과 관련된 기능은 해당 기능을 사용하는 Flow 또는 Actor에서 시작해 System과 RoleModule의 관계를 확인합니다.

# 

# \---

# 

# \# 기본 구조

# 

# ```text

# SceneRoot

# &#x20;   │

# &#x20;   ▼

# Director

# &#x20;   │

# &#x20;   ▼

# Flow

# &#x20;   │

# &#x20;┌──┴───────────────┐

# &#x20;▼                  ▼

# Actor              Viewer

# &#x20;│

# &#x20;▼

# Module

# ```

# 

# SceneRoot는 Scene 내부 객체의 초기화와 조립을 담당합니다.

# 

# Director는 여러 Flow를 조율합니다.

# 

# Flow는 Actor, Viewer, System 등을 연결하여 플레이를 구성합니다.

# 

# Actor는 하나의 Unity 런타임 오브젝트와 그 내부 기능을 대표합니다.

# 

# Viewer는 UI와 화면 표현을 담당합니다.

# 

# Module은 Actor 내부의 구체적인 상태와 기능을 담당합니다.

# 

# \---

# 

# \# 각 객체의 역할

# 

# \## SceneRoot

# 

# Scene에서 사용되는 객체를 초기화하고 연결합니다.

# 

# 초기화 순서와 Scene 진입·종료를 관리합니다.

# 

# SceneRoot는 플레이 기능을 직접 수행하기보다, 이미 구성된 객체들이 올바른 순서로 동작할 수 있도록 조립합니다.

# 

# \---

# 

# \## Director

# 

# 여러 Flow의 실행 순서, 전환, 생명주기를 조율합니다.

# 

# 개별 기능을 직접 수행하기보다 독립적으로 실행할 수 있는 Flow들을 조합하여 더 큰 플레이 단위를 구성합니다.

# 

# \---

# 

# \## Flow

# 

# 여러 객체 사이의 실행 흐름과 게임 규칙을 담당합니다.

# 

# Actor, Viewer, System 등 서로 다른 영역의 기능을 연결하여 하나의 플레이 기능을 구성합니다.

# 

# Flow는 하나의 Unity 오브젝트 내부보다 여러 객체 사이에서 발생하는 상호작용에 집중합니다.

# 

# \---

# 

# \## Actor

# 

# 하나의 Unity 런타임 오브젝트를 대표합니다.

# 

# 내부 Module을 초기화하고 연결하며, 외부 실행 흐름과 내부 기능 사이의 경계가 됩니다.

# 

# Actor는 자신을 구성하는 Module의 구체적인 관계를 알고 조립할 수 있습니다.

# 

# \---

# 

# \## Module

# 

# Actor 내부의 구체적인 상태와 기능을 담당합니다.

# 

# Module은 가능한 한 자신이 몰라도 되는 외부 객체와 계층의 구체 타입에 의존하지 않습니다.

# 

# 외부에 요청이 필요하다면 자신에게 필요한 기능만 Handler를 통해 전달합니다.

# 

# \---

# 

# \## System

# 

# 같은 역할을 수행하는 RoleModule들을 등록하고 조회합니다.

# 

# System은 Actor 내부의 구체적인 Module 구성이나 플레이를 실행하는 Flow를 알지 않습니다.

# 

# System은 등록된 RoleModule이 제공하는 공통 역할을 기준으로 기능을 수행합니다.

# 

# \---

# 

# \## Viewer

# 

# UI와 화면 표현을 담당합니다.

# 

# Viewer는 Module의 상태를 직접 관찰할 수도 있고, Flow나 Director의 명령을 받아 표현을 실행할 수도 있습니다.

# 

# 연결 방식보다 중요한 것은 동일한 표현 상태를 여러 객체가 동시에 제어하지 않도록 최종 책임을 명확히 하는 것입니다.

# 

# \---

# 

# \# 기본 개발 방식

# 

# 초기에는 각 Flow, Actor, Viewer가 필요한 참조를 `SerializeField` 또는 `Init()`을 통해 직접 받도록 구성합니다.

# 

# 가능한 경우 상위 객체가 없어도 자신의 기능을 실행할 수 있게 만듭니다.

# 

# ```text

# Flow

# = 필요한 Actor, Viewer, System이 주어지면 실행할 수 있음

# 

# Actor

# = 필요한 Module과 외부 연결이 주어지면 동작할 수 있음

# 

# Viewer

# = 관찰할 상태나 표현 요청이 주어지면 동작할 수 있음

# ```

# 

# Director는 Flow의 기능을 가능하게 만드는 객체가 아닙니다.

# 

# 이미 독립적으로 동작할 수 있는 여러 Flow의 실행 순서와 전환을 조율합니다.

# 

# SceneRoot 역시 각 기능을 직접 수행하지 않습니다.

# 

# 객체가 많아지고 초기화 순서나 참조 연결을 한곳에서 관리할 필요가 생겼을 때 SceneRoot에서 조립합니다.

# 

# 작은 기능을 구현하기 위해 처음부터 모든 상위 계층을 만들 필요는 없습니다.

# 

# \---

# 

# \# 몰라야 하는 계층에 접근하기

# 

# 객체가 상대의 구체 타입을 알아도 책임과 재사용성에 문제가 없다면 직접 참조할 수 있습니다.

# 

# 하지만 자신이 몰라도 되는 외부 계층에 요청해야 한다면 Handler 인터페이스를 사용합니다.

# 

# ```text

# Module

# &#x20;   ↓

# Handler

# &#x20;   ↓

# Actor 또는 Flow

# ```

# 

# Handler는 모든 의존성을 인터페이스로 바꾸기 위한 규칙이 아닙니다.

# 

# 현재 객체가 몰라도 되는 외부 구현을 감추면서, 자신에게 필요한 요청만 전달하기 위한 경계입니다.

# 

# 예를 들어 Module은 자신의 기능을 실행하기 위해 외부에 요청해야 할 수 있지만, 그 요청을 처리하는 대상이 어떤 Actor인지 또는 어떤 Flow인지는 알 필요가 없을 수 있습니다.

# 

# 이 경우 Module은 구체 타입 대신 Handler만 알고 요청을 전달합니다.

# 

# ```text

# Module이 알아야 하는 것

# = 자신이 보낼 수 있는 요청

# 

# Module이 몰라도 되는 것

# = 요청을 처리하는 구체 객체와 외부 플레이 구조

# ```

# 

# Handler는 Module마다 반드시 별도로 만들 필요는 없습니다.

# 

# 여러 Module이 같은 문맥에 속하고 비슷한 요청을 사용한다면 공통 Handler로 묶을 수 있습니다.

# 

# 반대로 Handler가 서로 관련 없는 기능까지 포함하며 지나치게 커진다면 실제 역할 경계에 따라 분리를 고려합니다.

# 

# \---

# 

# \# System과 RoleModule

# 

# System은 Actor를 직접 관리하지 않고 RoleModule을 관리합니다.

# 

# RoleModule은 System에서 사용하기 위해 Actor에 추가되는 Module입니다.

# 

# ```text

# System

# &#x20;   ↓

# RoleModule

# &#x20;   ↓

# Handler

# &#x20;   ↓

# Actor

# ```

# 

# System은 RoleModule을 통해 공통된 역할을 조회하거나 요청합니다.

# 

# RoleModule은 System의 요청을 Actor가 이해할 수 있는 Handler 요청으로 변환합니다.

# 

# 이를 통해 System은 다음 내용을 알 필요가 없습니다.

# 

# ```text

# Actor의 구체 타입

# 

# Actor 내부의 Module 구성

# 

# Actor가 요청을 처리하는 방법

# 

# Actor가 연결된 Flow

# 

# 현재 플레이의 구체적인 진행 방식

# ```

# 

# System은 Actor 전체가 아니라 자신에게 필요한 역할만 다룹니다.

# 

# RoleModule은 System과 Actor 사이에서 해당 역할을 표현하는 어댑터가 됩니다.

# 

# 현재 구조에서는 System이 관리하는 대상을 RoleModule로 한정합니다.

# 

# 다른 종류의 Module을 System이 직접 관리할 필요가 실제로 생기기 전까지는 범위를 확장하지 않습니다.

# 

# \---

# 

# \# 복잡해질 때 확장하기

# 

# 초기에는 하나의 Flow가 여러 게임 규칙을 담당해도 됩니다.

# 

# 현재 구조가 충분히 읽기 쉽고 수정하기 쉽다면 그대로 유지합니다.

# 

# 책임을 분배한다는 이유만으로 처음부터 모든 기능을 별도 객체로 만들 필요는 없습니다.

# 

# 다음과 같은 문제가 실제로 나타날 때 책임 이동을 고려합니다.

# 

# ```text

# 서로 관계없는 참조가 계속 늘어남

# 

# 기능마다 필요한 생명주기가 달라짐

# 

# 일부 기능을 다른 Scene이나 GameMode에서 재사용해야 함

# 

# 하나의 기능을 수정할 때 다른 기능까지 함께 확인해야 함

# 

# 객체 이름만으로 내부 책임을 설명하기 어려움

# ```

# 

# 하나의 Flow가 커졌더라도 내부 기능의 경계가 구분되어 있다면 필요한 책임을 새로운 Flow로 이동할 수 있습니다.

# 

# ```text

# 하나의 큰 Flow

# &#x20;   ↓

# 실제로 복잡해진 책임을 식별

# &#x20;   ↓

# 해당 책임과 참조를 새로운 Flow로 이동

# ```

# 

# 여러 Flow의 실행 순서와 전환이 복잡해지면 Director를 추가하거나 기존 Director로 책임을 이동합니다.

# 

# ```text

# 독립적인 플레이 기능

# → Flow

# 

# 여러 Flow의 순서와 전환

# → Director

# ```

# 

# 초기화 순서와 Scene 전체의 참조 연결이 복잡해지면 SceneRoot에서 관리합니다.

# 

# ```text

# 객체의 개별 초기화

# &#x20;   ↓

# 초기화 관계가 복잡해짐

# &#x20;   ↓

# SceneRoot에서 조립

# ```

# 

# 확장은 새로운 구조를 처음부터 다시 만드는 방식이 아닙니다.

# 

# 기존 객체에서 복잡해진 책임과 참조를 적절한 객체로 이동하는 방식으로 진행합니다.

# 

# \---



# \# 핵심 원칙

# 

# > 이 구조의 목적은 책임을 분배하기 위해 객체를 많이 만드는 것이 아닙니다.

# >

# > 작은 구조로 플레이를 먼저 완성하고, 복잡해진 책임을 적절한 위치로 쉽게 이동할 수 있도록 만드는 것이 목적입니다.

# 

# ```text

# 객체 내부의 상태와 기능

# → Module

# 

# System에서 사용되는 Actor의 역할

# → RoleModule

# 

# 역할의 등록과 조회

# → System

# 

# 하나의 Unity 오브젝트 구성

# → Actor

# 

# 화면과 연출

# → Viewer

# 

# 객체 사이의 플레이 규칙

# → Flow

# 

# 여러 Flow의 순서와 전환

# → Director

# 

# Scene 초기화와 조립

# → SceneRoot

# ```

# 

# 처음부터 책임을 모두 나누지 않습니다.

# 

# 먼저 플레이를 구현하고, 실제로 드러난 경계를 따라 책임을 이동하며 확장합니다.
