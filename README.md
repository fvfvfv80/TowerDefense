# Tower Defense - Architecture Refactoring

## 프로젝트 소개

유튜브 **'고박사의 유니티 노트'** 채널의 타워 디펜스 게임 개발 영상을 기반으로 제작한 프로젝트입니다.

교육을 위해 기능 구현 중심으로 작성된 타워 디펜스 코드를 바탕으로, 실제 게임 개발에서 **확장성, 유연성, 생산성**을 고려한 구조로 리팩터링하고 있습니다.

단순히 기능을 분리하는 것보다, **기능의 확장과 영역 간 관계의 변화를 서로 다른 문제로 다루면서도 개발 비용이 과도하게 증가하지 않는 구조**를 목표로 합니다.


## 구조 소개

**Director / Actor를 중심으로, 내부 기능은 Gameplay / Module로 분리하고 외부 영역과의 관계는 Flow를 통해 구성합니다.**

```text
                  Flow
        ─────────────────────
          영역 간 관계 / 조합
             플레이 흐름

          ↓               ↓

      Director           Actor
         │                 │
    ┌────┴────┐       ┌────┴────┐
 Gameplay   Module   Gameplay   Module
```

### Director / Actor

각 게임플레이 영역과 Unity 객체의 중심이 되는 **Host**입니다.

필요한 기능을 직접 구현할 수도 있고, 책임이 커지거나 분리가 필요해지면 Gameplay / Module을 조합하여 확장합니다.

### Gameplay / Module

Director / Actor가 가진 기능과 책임을 세분화하는 구성 요소입니다.

가독성, 확장, 재사용 등의 필요에 따라 분리하며, Host와 느슨하게 연결할 필요가 있다면 **Host Interface를 통해 필요한 기능만 계약**할 수 있습니다.

### Flow

서로 독립적인 Director / Actor 사이의 **관계와 플레이 흐름을 구성**합니다.

각 영역이 다른 영역의 구체적인 구현에 직접 의존하지 않도록 중재하며, 필요한 경우 Interface를 통해 연결할 영역의 기능만 계약합니다.

Flow는 게임의 모든 진행 상태를 관리하기보다, **독립적인 게임플레이 영역을 연결하고 조합하는 역할**에 집중합니다.


## 개발 방향

### 기능과 관계의 변화를 분리

기능 자체를 확장하기 좋은 구조를 만들더라도, 하나의 객체가 다른 영역과의 관계까지 책임한다면 관계가 변할 때 기존 구현을 다시 수정해야 할 수 있습니다.

이 프로젝트에서는 **내부 기능의 확장은 Gameplay / Module**, **외부 영역과의 관계 변화는 Flow**를 중심으로 다루어 두 종류의 변화를 분리합니다.

이를 통해 기능의 **확장성**과 영역 간 관계 변화에 대한 **유연성**을 함께 확보하는 것을 목표로 합니다.


### 독립적으로 개발하고 나중에 연결

다른 영역의 구현이 완료될 때까지 기다리지 않고, 필요한 경우 Interface를 통해 계약을 먼저 정의하여 각 영역을 독립적으로 개발할 수 있도록 합니다.

각 영역은 가능한 한 자신의 책임 안에서 먼저 구현하고 검증한 뒤, 필요한 관계를 Flow를 통해 연결하여 실제 플레이를 구성합니다.

이를 통해 여러 영역을 병렬적으로 개발하고 개별 기능을 독립적으로 검증할 수 있는 **생산성 높은 개발 방식**을 지향합니다.


### 필요한 만큼만 구조화

확장성과 유연성을 위해 구조를 지나치게 세분화하면 오히려 개발 비용과 복잡도가 증가할 수 있습니다.

모든 기능을 처음부터 Gameplay, Module, Flow, Interface로 분리하지 않고, 먼저 필요한 기능을 구현한 뒤 **책임 증가, 재사용, 협업, 결합 문제 등 실제 필요가 생기는 시점에 구조를 점진적으로 분리하고 확장**합니다.

이를 통해 확장성과 유연성을 위한 구조적 선택이 **개발 생산성을 해치지 않도록 필요한 만큼의 구조를 사용하는 것**을 목표로 합니다.
